# TibiaNerd Constitution

## Core Principles

### I. English Project, Portuguese Site

- Code, comments, tests, commits, branches, pull requests, issues and documentation MUST be
  in English.
- Text shown to users on the site MUST be in Brazilian Portuguese.

Rationale: the project stays readable internationally while serving Brazilian players.

### II. Tools Without Sign-Up

- Calculators and lookups MUST be usable without login, account or configuration.
- Login MAY exist only for features that need an identity, such as saved characters and
  party ads.
- Browser storage MAY keep conveniences, but a tool MUST keep working when storage is
  missing or blocked.

Rationale: people who only want the tool can open it and use it.

### III. Separate, Traceable Game Data

- Game tools start with Tibia Global. Other servers MAY be added as a choice for the player.
- The party finder covers Tibia and RubinOT, and matches only within one server and world.
- Data from different servers MUST never be mixed.
- Every data set MUST state its source and review date.
- Game data MUST be generated by scripts and stored in the repository.
- The published site MUST NOT depend on external game data APIs at runtime, except to look
  up a character at the request of a signed-in player.
- A screen using data from one server MUST say which server it covers.

Rationale: wrong numbers break trust, and the two servers can differ.

### IV. Pure, Tested Domain Logic

- Formulas, parsers and optimizers MUST live in `src/domain` as pure functions.
- Every domain function MUST have unit tests.
- A calculator or optimizer MUST be checked against a known reference result when one exists.
- Components MUST NOT hold game rules.

Rationale: game rules are the core value of the site and must be testable without a browser.

### V. Mobile First and Accessible

- Every page MUST work at 375 px without horizontal scrolling.
- Tap targets MUST be at least 2.75rem tall.
- Text MUST meet WCAG AA contrast.
- Animations MUST respect reduced motion preferences.
- Interactive elements MUST work with a keyboard and have accessible names.

Rationale: many players use the site on a phone next to the game.

### VI. Fan Site Compliance

- The site MUST state that Tibia is made by CipSoft, that official graphics are copyrighted
  by CipSoft, and link to both.
- The site MUST NOT promote cheats or real-money trading.
- Game images MUST appear only inside tools, never as a separate gallery or download.
- Every game image MUST have a replacement that can be restored without changing components.
- The Tibia logo MUST NOT be used.
- TibiaWiki data MUST keep its CC-BY-SA attribution.

Rationale: the project depends on CipSoft's tolerance and must be able to remove assets fast.

### VII. Honest Interface

- The site MUST NOT show invented numbers, statistics or activity.
- Unfinished tools MUST be labeled as unavailable.
- Results MUST state the assumptions and limits that affect them.

Rationale: players act on these numbers, so the site must not imply more than it knows.

### VIII. Research Before Recommending

- Web decisions MUST start with a search for how senior web developers solve the problem.
- Recommendations MUST come with their source when one exists.

Rationale: the maintainer is a senior iOS developer who is new to web and wants to learn.

### IX. Minimal Personal Data

- Features MUST collect only the personal data they need.
- A privacy page and account deletion MUST be live before login reaches users.
- Personal data MUST NOT be sold or shown beyond what its owner chose to publish.

Rationale: a login turns a fan site into a keeper of other people's data.

## Technical Constraints

- The stack is Astro with static pages by default, React islands, strict TypeScript, CSS
  Modules, Vitest and Playwright.
- On-demand routes MAY serve login and shared data, on Cloudflare Workers with D1.
- New dependencies MUST solve a need the current stack cannot solve simply.
- Spec Kit files, this constitution and feature specs MUST be committed, so they follow the
  repository to any machine.

## Development Workflow

- Local verification is not required, because CI runs every check.
- CI MUST run type checks, unit tests, the build and UI tests.
- Changes MUST reach `main` through a pull request.
- Every pull request MUST open ready for review, unless the maintainer asks for a draft.
- A ready pull request merges automatically when CI passes.
- Pull request descriptions MUST stay short, and screenshots MUST be few and current.

## Governance

This constitution takes precedence over other project practices. `AGENTS.md` holds runtime
guidance and MUST stay consistent with it.

Amendments require the maintainer's approval and a version change:

- MAJOR: a principle is removed or redefined incompatibly.
- MINOR: a principle or section is added or materially expanded.
- PATCH: wording changes without a change in meaning.

Every feature plan MUST check compliance with these principles. Any exception MUST be
justified in that plan.
